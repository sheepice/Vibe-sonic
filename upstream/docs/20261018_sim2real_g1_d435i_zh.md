## 1. 当前框架与真机目标

目标链路是：

```text
键盘 W 按住 / 松开
    ↓ 前向速度请求
SONIC 在线规划器（5 Hz，生成未来行走参考）
    ↓ 10 个参考帧：当前至未来 0.9 秒，每 0.1 秒一个
SONIC 参考编码器 → FSQ 运动 token
                       ↘
G1 IMU、29 关节状态、历史动作 → 冻结 SONIC 解码器＋ViBe 适配器 → 29 维动作
D435i RGB → 冻结 Theia → 视觉查询/注意力 ↗                    ↓
独立速度指令 8 维（仅当前速度版） ──────────────────────→ 默认姿态＋缩放×动作
                                                             ↓
                                               目标限位/变化率检查 → G1 PD 控制
```

操作者不用提供楼梯动作文件，但**模型内部仍然使用在线参考动作**。相机负责给适配策略提供视觉条件，规划器本身不读楼梯高度图。当前 actor 不需要世界坐标位置、真实根节点线速度、深度或地形扫描；仿真评估使用这些量计算成绩，不代表真机 actor 有这些输入。

本轮代码只开放向前速度和停止。没有把横移、倒退、转弯训练成经过验证的功能，不能因为 SONIC 上游支持 WASD 就直接给当前速度适配器开放完整 WASD。

## 3. 模型输入输出的精确定义

batch 固定为 1，输入 float32，视觉编码器输入例外。

| 输入 | 形状 | 内容 |
|---|---|---|
| `policy` | 1×930 | 10 帧历史：角速度 30、相对关节位置 290、关节速度 290、上一动作 290、重力方向 30 |
| `tokenizer` | 1×640 | 10 帧未来关节位置/速度与骨盆相对参考旋转 |
| `augmentation` | 1×6 | 参考根节点线速度和角速度，表达在**参考根节点自身坐标系** |
| `kv_tokens__img_tokens` | 1×21×192 | Theia 图像 patch token |
| `q_task_cmd` | 1×6 | 当前导出图中的参考 twist 查询，与 augmentation 相同；某些官方图已去重此端口 |
| `q_proprio` | 1×64 | 重力 3＋角速度 3＋相对关节位置 29＋关节速度 29 |
| `q_cls` | 1×192 | Theia CLS token |
| `velocity_command` | 1×8 | 仅速度版；下文给出语义 |

速度版在线组输入为 `[v cosψ, -v sinψ, 0, 1-cosψ, -sinψ, 1, 0, 0]`。ψ 是机器人相对于开始控制时固定朝向的偏航，最后三项是 online/paired/flat 任务标记。不要误写成 `[vx,vy,wz,cosψ,sinψ,...]`，不要每帧重新清零朝向。

历史按**每一种观测单独存 10 帧，再拼接各项**，时间从旧到新；初始化复制第一帧。不是把 93 维整帧连续铺 10 次。Tokenizer 也有特殊布局：先拼全部未来关节位置和全部未来关节速度，再 reshape 成 10×58，最后每行追加 6D 旋转。新代码已按训练源实现，并在物理仿真中逐项对照。

输出是 29 维无量纲动作 `a`，换算 `q_des = q_default + action_scale * a`。单位是 rad，**不是角度、力矩或关节速度**。SDK 写入 `dq=0, tau=0`，采用导出的 Kp/Kd。不要把 Unitree 示例的 PD 值抄来替换训练配置。

低层模式为 PR，即踝关节/腰部的 pitch-roll 关节表达；`mode_machine` 从实机 LowState 复制。SDK 消息用 `unitree_hg`。协议依据 [Unitree SDK2 Python G1 示例](https://github.com/unitreerobotics/unitree_sdk2_python/blob/master/example/g1/low_level/g1_low_level_example.py)。

关节顺序完整保存在 `bundle.json`：左腿 6、右腿 6、腰 yaw/roll/pitch 3、左臂 7、右臂 7。SDK motor index 与本包 MJ 顺序一致；IsaacLab 数据文件必须按名字转换后使用。

## 6. D435i 安装、图像与标定

训练相机安装在 `torso_link`，相对位置 `(0.05, 0, 0.4318)` 米，MuJoCo 相机四元数 wxyz 为 `(0.6533, 0.2706, -0.2706, -0.6533)`，大致向前下方 45°。这是相对 torso 的位置，**不是离地高度**。输出 112×63，垂直 FOV 42.5°。

相机要求 RGB，深度没有接入当前 actor。D435i 的自身 IMU 也没有替代 G1 骨盆 IMU。RGB 与 depth 的视场不同，不要使用 depth 内参裁 RGB。

新接入默认采 RGB 1280×720、30 FPS、BGR8；用设备的 RGB 内参/畸变模型把像素重采样为 42.5° 视场，而非把 4:3 图像压扁成 16:9。编码器内部再做 BGR→RGB、除 255、ImageNet 标准化。不要在外面重复归一化。RealSense 采集接口见 [官方 config API](https://realsenseai.github.io/librealsense/python_docs/_generated/pyrealsense2.config.html)。

先仅打开相机，不连接控制：

```bash
cd /mnt/workspace/wjw/GRAIL/vibe_grail_joint
.venv-real/bin/python -m vibe_grail_joint.deploy.camera \
  --seconds 10 --output records/real_camera_check_01
```

检查输出 `policy_rgb.png` 和 `camera_report.json`。图像应能看到机器人前方落脚区域、台阶立面和踏面，不能上下颠倒、通道反色或大量遮挡。记录设备 serial、RGB 内参、实际 FPS；多相机时使用 `--serial` 指定。

复制安装参数模板：

```bash
cp deployment/camera_mount.example.json deployment/my_g1_camera.json
```

把 serial、实测 pos/quat 填入；确认完成测量后，将 `measurement_source` 写为 `measured_on_robot`。示例故意标为未测量，不能直接拿来启用电机。`validate_mount` 仅做名义位置 2 cm、姿态 5° 的粗检查；这个阈值不能替代外参标定或证明策略泛化。

注意坐标：MuJoCo 相机轴是 X 右、Y 上、-Z 前；OpenCV/RealSense optical 是 X 右、Y 下、Z 前。若测得 `R_torso_optical`，填写前先算 `R_torso_mujoco = R_torso_optical × diag(1,-1,-1)`，再转为 wxyz。测量应针对 RGB 光心。安装位置不同不能靠随意修改 JSON 变成已对齐，应调整安装或在该安装参数下补训练。

相机占用时先查明是哪个服务。原版 `camera_streamer.py` 会尝试停止 Unitree video 服务；本次新增代码**不会自动停止系统服务**。只有确认本机服务确实占用该相机后，由现场操作员按机器人系统文档处理。

## 8. 物理仿真验收

GPU 空闲时执行。脚本先检查占用并持有锁，不会终止别人的训练：

```bash

  --bundle exports/20261018_sim2real_velocity3999 \
  --config runs/20261018_vibe_posture_speed_refine/config.json \
  --mode parity --gpu 0 --seconds 2 \
  --output records/my_sim2real/parity.json

.venv/bin/python -m vibe_grail_joint.deploy.simcheck \
  --bundle exports/20261018_sim2real_velocity3999 \
  --config runs/20261018_vibe_posture_speed_refine/config.json \
  --mode keyboard --terrain flat --actuator-guards --gpu 0 --seconds 12 \
  --output records/my_sim2real/start_stop_flat.json
```

第二项从静止默认姿态开始，2 秒按 W，8 秒松开，完整观察至 12 秒。不是从已经走动的参考中间开始。增加 `--terrain up`、`down`、`up_down` 可换路面，但默认 6 秒行走未必能走完整段楼梯；报告中的 survival 不等于全程通关。

较长楼梯试验可使用 `--seconds 39 --walk-seconds 35`，并换一个新的输出文件名。测试会在跌倒或保护触发时提前结束；进程退出码 0 可能只是成功写完报告，必须检查 JSON 中的 `fall`、`guard_stop_reason`、完整运行时间和位移。`simcheck` 不会把“没有摔倒但停在第一阶前”记成通关。

当前仿真器不是 Unitree 原生仿真器，也不包含真实 DDS 延时/电机固件/相机曝光。先用本工具查输入和起停，再使用原版教程的 `unitree_mujoco` 进行独立仿真验证。

训练视觉为 FP16，而 ONNX 视觉为 FP32。报告同时给出训练特征差异和 CPU FP32→ONNX 误差，不把两者混算成观测布局错误。ONNX 中 FSQ 有离散量化边界，两个物理分支不会因为开环误差很小就逐帧完全相同。

## 10. 影子推理，不发电机指令

```bash

  --bundle exports/20261018_sim2real_velocity3999 \

```

需要本机图形桌面或可靠转发的 SDL 窗口；纯无图形 SSH 终端不支持这个按键释放检测。先让窗口获得焦点，Enter 启用虚拟指令，按住 W，再松开。日志 `lowcmd_enabled` 应始终为 false。

影子模式的机器人不跟随预测动作，因此其长期闭环历史不代表真实受控轨迹；它主要查传感器、时序、计算和接口。检查相机 frame_id 持续增加、日志速度确实回零、动作有限、实际整条周期足够快。在支撑/影子阶段分别拔相机、断网络、切窗口，验证程序记录故障，不能用正常工况一次运行代替断连检查。

```bash
  --acceptance-report records/my_sim2real/start_stop_flat.json \
  --provider cpu --speed 0.25 --seconds 60 \
  --log records/g1_supported_control_01.jsonl
```

程序默认不夺取现有控制器。若确认需要由此程序接管，且现场已完成支撑和控制权交接，可额外指定 `--release-sport-mode`；它在 Enter 接管时调用 MotionSwitcher，检查释放结果。禁止同时启动本 Python 控制器、官方 C++ tracker、原 SONIC deploy 或其他低层控制器。

报告必须对应同一 policy/encoder/planner 字节、机器人 PD/动作缩放、相机配置和保护参数，且完整经过静止→前进→停止。控制速度不能超过报告中测试过的速度；0.25 m/s 的报告不放行 0.4/0.7 m/s。这个自动检查只是工程前置条件，不会证明真实环境或其他楼梯已通过。

1. 启动时观察窗口和日志，先不按 W。
2. 在已支撑、接近默认姿态、静止的状态下按 Enter。当前程序不提供从趴地/坐姿自动站起；姿态偏差过大将拒绝接管。
3. 程序用 3 秒从当前关节角过渡到训练默认姿态，然后进入策略控制。这个姿态过渡本身也需要现场验证，不能用仿真默认初始状态代替。
4. 确认站立稳定，再按住 W 请求向前；默认 0.25 m/s，命令按每步 0.01 m/s 变化，进入在线参考和速度分支。
5. 松开 W 或按空格请求停止，规划器切到 stand 模式。仅把 planner 的 `target_vel` 填 0 并不能停，因为 SONIC 将非正值解释为模式默认值；代码同时设置 `mode=0`。
6. Esc、窗口失焦、遥控 SELECT 或健康检查失败会锁存故障并请求阻尼。程序不会自动恢复行走，重启前要排查原因。

松开 W 是“规划并执行停步”，不是让关节瞬间锁死，仍有减速和迈完支撑步的距离。下楼时尤其不能指望松键后立即停在台阶边缘；先在平地测量停步距离。

策略 50 Hz，SDK writer 500 Hz 重复最近目标；状态、相机、按键、策略目标超时分别为 50/150/150/60 ms。关节目标允许小幅投影到物理限位，并限制每 20 ms 最大目标变化 0.20 rad；投影过大仍拒绝。实际执行动作再回写历史，所有投影写日志。该处理改变训练时未限制目标的控制行为，因此必须使用 `--actuator-guards` 做闭环测试，不能只看未受限制的成功录像。

`mode_machine` 控制中变化、SDK 写入失败、温度或电机错误也会锁存故障。训练仿真里的 effort limit 保存在 manifest 中；真实固件如何限流/限力矩、PD 标定是否一致仍须核对，不能把有限位置目标等同于真实力矩一定合适。

阻尼 Kp=0，Kd 为训练 Kd 与 2 的较小值；**阻尼会失去站立支撑，必须有吊带/保护人员**。SIGKILL、进程崩溃、机器断电、Python GIL 或内核调度失控时，Python watchdog 不能保证执行，应有机器人侧独立超时/急停。退出时只尝试短暂阻尼交接，不宣称保持姿态。

## 12. 从平地到楼梯

先通过：静止站立 → 平地 0.25 m/s → 松键停车 → 重复起停 → 小高度单台阶 → 连续低台阶 → 上楼/下楼分别测试 → 上下组合。台阶表面需有足够摩擦和踏面，初期由现场保护，不直接从 25/30 cm 的仿真示例开始。

每种条件记录：模型 SHA、相机外参/内参、台阶各级高度与踏面、速度指令、真实前进距离/时间、停步距离、腰/手臂偏差、是否触发限位或超时、是否有人辅助。成功片段之外，失败和中断也保留，统计分母包含所有尝试。

没有外部定位时，本 actor 仍能运行，但“实测速度、位移、偏航漂移”验收需要独立测量，例如标尺/外部录像/定位；不能把输入速度当成机器人实际速度。

## 13. 哪些情况需要补训练

若站立/起停失败：增加从默认静止姿态启动、站立→行走→站立的参考和命令切换训练，减少只用行走中段初始化的偏差。若上身受损：继续保持腰/臂分组参考损失和姿态项，不能只增加向前奖励。

若相机换装：用实测外参重建相机，并增加曝光、颜色、纹理、模糊、帧率、延迟/丢帧随机化；当前 30 FPS 真相机与训练每控制步图像的差异要单独验证。若执行目标经常限幅：把同样的执行约束加入训练环境，检查上肢保持损失、腿部动作速率、接触与扭矩参数，避免部署阶段不断扩大阈值掩盖问题。

若希望任意方向或更大速度：加入对应独立指令和随机朝向/转弯任务再训练。目前上楼能力不代表“任意楼梯、任意方向、任意速度都能通过”。

## 14. 常见问题定位

| 现象 | 优先检查 |
|---|---|
| 读不到 LowState | 有线网口、DDS domain 0、网段、固件是否开放底层接口、是否选错设备 |
| 肢体交叉或抖动 | IL/MJ 关节顺序、rad/deg、默认姿态、PD/action_scale；不要先调 reward |
| 抬腿方向异常 | 骨盆 IMU wxyz、重力方向、参考旋转、固定开始朝向 |
| 看得到 RGB 但表现变差 | optical/MuJoCo 外参、FOV、遮挡、曝光、BGR/RGB、是否重复标准化 |
| 松 W 仍继续行走 | UI 焦点、日志命令、planner mode 是否 0、参考延迟与停步距离 |
| `target_discontinuity` / `excessive_target_slew` | 参考切换连续性、实际动作历史、策略起停分布；保留日志后再改算法 |
| `stale_camera` | 设备占用、USB 带宽、长曝光、帧号停滞；不能简单一直复用最后一帧 |
| `policy_watchdog` | CPU 争用、ORT provider、日志磁盘、planner 是否异步、线程调度 |
| CUDA 不可用 | ORT GPU 包与 CUDA/cuDNN；不要把自动 CPU 回退当作 GPU 成功 |

所有新测试记录在 `records/20261018_sim2real/`。原始失败报告保留，后续修复的结果使用新文件名，不覆盖成“全部成功”。
